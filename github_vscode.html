Trabajo colaborativo con GitHub y VS Code

Guía práctica para trabajar sobre un mismo proyecto sin sobrescribir el trabajo de otras personas, conservando un historial claro y revisable.

1. Actualizar main2. Crear rama3. Programar4. Revisar5. Commit6. Publicar7. Pull Request8. Revisión9. Merge

Objetivo

El flujo que repetiremos siempre

Nadie programa directamente sobre main. Cada cambio nace en una rama, se revisa mediante un Pull Request y solo entonces se integra.

main al día
rama propia
PR revisado
merge + limpiar
Idea claveGit administra cambios en la computadora; GitHub conecta ese trabajo con el equipo.
1

Git, GitHub y repositorio

Git

Programa de control de versiones instalado localmente. Guarda estados del proyecto, compara cambios y administra ramas.

GitHub

Servicio web que aloja repositorios Git y añade colaboración: Pull Requests, revisiones y permisos.

Repositorio

Carpeta de proyecto controlada por Git junto con su historial. Tiene copia local y, normalmente, copia remota.

AnalogíaGit es el sistema de seguimiento; GitHub es el punto de encuentro; el repositorio es el proyecto con su historial.

Preparación inicial en Windows

Instalar Git

  1. Descargue Git for Windows desde git-scm.com.
  2. Ejecute el instalador conservando las opciones recomendadas.
  3. Cierre y vuelva a abrir VS Code.
  4. Abra Terminal → New Terminal y verifique:
Terminal integrada
git --version
Si “git no se reconoce”Reinicie VS Code o Windows. Si continúa, reinstale Git permitiendo su uso desde la línea de comandos.

Configurar nombre y correo

Configuración global
git config --global user.name "Nombre Apellidos"
git config --global user.email "correo@ejemplo.com"
git config --global init.defaultBranch main
git config --global --list

Cuenta de GitHub

  1. Cree la cuenta en github.com.
  2. Verifique el correo recibido.
  3. Active autenticación en dos pasos.
  4. Use un nombre reconocible para el equipo.

Iniciar sesión en VS Code

  1. Pulse el icono de cuentas, abajo a la izquierda.
  2. Elija Sign in with GitHub.
  3. Autorice VS Code en el navegador.

Extensión oficial

Abra Extensiones con Ctrl + Shift + X, busque GitHub Pull Requests, compruebe que el publicador sea GitHub e instálela.

Repositorio del grupo y .gitignore

Una persona crea en GitHub un repositorio con nombre corto, la visibilidad indicada por el docente y un archivo README.

.gitignore

Este archivo, ubicado en la raíz, indica qué contenido Git no debe rastrear.

11–13

Invitar, aceptar y clonar

Responsable

Repositorio → Settings → Collaborators → Add people. Busque el usuario y envíe la invitación.

Cada integrante

  1. Acepte la invitación.
  2. En VS Code pulse Ctrl + Shift + P.
  3. Ejecute Git: Clone y seleccione Clone from GitHub.
  4. Elija el repositorio y la carpeta madre.
  5. Seleccione Open y abra el proyecto clonado.
Equivalente Git
git clone https://github.com/organizacion/proyecto.git
cd proyecto
code .
Clone se usa una sola vez por computadoraLuego se actualiza con pull. No descargue ZIP ni clone repetidamente.
14

Control de código fuente

Abra la vista con Ctrl + Shift + G.

  • Changes: archivos modificados aún no preparados.
  • Staged Changes: archivos elegidos para el próximo commit.
  • Message: descripción del cambio.
  • Commit: crea el registro local.
  • ⋯: ofrece Pull, Push y otras operaciones.
IndicadoresM modificado, U nuevo, A agregado y D eliminado.
15–17

Actualizar main y crear una rama

Actualizar main

  1. Pulse el nombre de rama en la barra inferior y cambie a main.
  2. Use Sync Changes o Source Control → ⋯ → Pull.
  3. Confirme que no haya cambios pendientes.
Equivalente Git
git switch main
git pull origin main
git status

Crear y cambiar de rama

  1. Pulse main en la barra inferior.
  2. Elija Create new branch….
  3. Escriba un nombre descriptivo.
PrefijoUsoEjemplo
feature/Funcionalidadfeature/formulario-contacto
fix/Correcciónfix/total-factura
docs/Documentacióndocs/instalacion
Equivalente Git
git switch -c feature/formulario-contacto
Antes de editarLa barra inferior debe mostrar su rama, nunca main.

Revisar cambios y crear commits

Seleccione un archivo en Changes: rojo representa líneas eliminadas y verde líneas agregadas.

  1. Implemente y pruebe una unidad pequeña.
  2. Revise visualmente cada diferencia.
  3. Pulse + para preparar los archivos.
  4. Escriba un mensaje específico en imperativo.
  5. Pulse Commit.
Equivalente Git
git status
git diff
git add pagina-ana.html
git diff --staged
git commit -m "Agrega estructura de la página de Ana"
Buen mensajePoco útil
Agrega validación del correocambios
Corrige cálculo del impuestoarreglo final 2
Commit no publicaEl commit queda local; push lo envía a GitHub.
20–21

Publish Branch, push, pull y Sync

  • Publish Branch: crea la rama remota la primera vez.
  • Push: envía commits locales.
  • Pull: trae e integra commits remotos.
  • Sync Changes: ejecuta pull y push.
Equivalentes
git push -u origin feature/formulario-contacto
git push
git pull
Guardar ≠ commit ≠ pushGuardar escribe el archivo; commit crea historial local; push lo publica.
22–24

Pull Request y revisión

Crear el PR desde VS Code

  1. Publique la rama y abra GitHub Pull Requests.
  2. Seleccione Create Pull Request.
  3. Base: main; compare: su rama.
  4. Describa qué cambió y cómo probarlo.
  5. En Reviewers, solicite revisión a otro integrante.
  6. Cree el PR.
Plantilla para el PR
## ¿Qué cambia?
- Agrega la página personal de Ana.

## ¿Cómo probar?
1. Abrir pagina-ana.html.
2. Probar enlaces y vista móvil.

## Lista de control
- [x] Probado localmente
- [x] Sin secretos ni archivos generados

Comentar, aprobar y fusionar

  1. Abra Files Changed y revise las diferencias.
  2. Comente líneas concretas con respeto.
  3. Elija Approve o Request changes.
  4. Las correcciones se hacen en la misma rama con nuevos commits y push.
  5. Tras la aprobación, use Merge Pull Request.
Revise el código, no a la personaExplique el problema y proponga una mejora verificable.
25–26

Después del merge: actualizar y limpiar

  1. Cambie a main.
  2. Ejecute Pull o Sync para recibir el merge.
  3. Pruebe el proyecto completo.
  4. Use Delete branch en el PR para borrar la rama remota.
  5. En VS Code use el selector → Delete Branch….
  6. Cree otra rama desde la nueva main para la siguiente tarea.
Equivalente Git
git switch main
git pull origin main
git branch -d feature/formulario-contacto
git push origin --delete feature/formulario-contacto
No reutilice ramas fusionadasCada tarea comienza en una rama nueva creada desde main actualizada.
27

Resolver conflictos visualmente

Un conflicto aparece cuando Git no puede decidir cómo combinar cambios sobre la misma zona.

  1. Abra el archivo marcado en Merge Changes.
  2. Seleccione Resolve in Merge Editor.
  3. Compare Current e Incoming.
  4. Acepte uno, ambos o construya manualmente el Result.
  5. Quite duplicados, pruebe y pulse Complete Merge.
  6. Prepare los archivos, haga commit y push.
Marcadores que no deben quedar
<<<<<<< HEAD
su versión
=======
versión entrante
>>>>>>> otra-rama
No use “Accept All” sin leerPuede duplicar código o descartar trabajo. Consulte a la otra persona si no comprende la intención.

29

Reglas recomendadas

  • No programar directamente en main.
  • Actualizar main antes de crear cada rama.
  • Una rama por tarea y nombre descriptivo.
  • Commits pequeños, probados y claros.
  • Revisar el diff antes del commit.
  • No publicar secretos ni dependencias generadas.
  • La persona autora no aprueba su PR.
  • Comunicar qué archivos se modificarán.
  • Después del merge: actualizar main y eliminar la rama.

Práctica guiada en clase

Producto: sitio del grupo con index.html y una página HTML por integrante. Cada persona hará dos commits, publicará su rama, abrirá un PR y revisará otro.

Preparación

  1. Crear el repositorio grupo-desarrollo-iv con README.
  2. Invitar al grupo.
  3. Agregar index.html y .gitignore.
  4. Publicar la base.

Trabajo individual

  1. Acepte, clone y abra el proyecto.
  2. Actualice main.
  3. Cree feature/pagina-nombre.
  4. Cree nombre.html con título, presentación, intereses y enlace al inicio.
  5. Commit 1: estructura y contenido.
  6. Agregue estilos o mejore accesibilidad. Commit 2.
  7. Pulse Publish Branch.
  8. Cree el PR, explique cómo probar y solicite revisor.

Ronda de revisión

  1. Cada persona revisa el PR de otro integrante.
  2. Deje al menos un comentario útil o una comprobación concreta.
  3. La persona autora corrige en la misma rama y hace push.
  4. Con aprobación, fusione y elimine la rama remota.
  5. Todo el grupo actualiza main y prueba el sitio.

Comprobación

  • Rama con nombre correcto.
  • Página funcional y adaptable.
  • Al menos dos commits claros.
  • Rama publicada.
  • PR con descripción y revisor.
  • Revisión realizada a otra persona.
  • PR aprobado y fusionado.
  • Main local actualizada.
  • Rama terminada eliminada.
